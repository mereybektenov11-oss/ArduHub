### Р2 (вопрос В2): игра — скачиваемое приложение для ПК

- Игра поставляется как **настольное приложение**, которое скачивают в профиле на сайте (`/app/profile/desktop`, кнопка там уже есть, сейчас неактивна).
- Маршрут `/play` на сайте **не делается**. Разделы 3.1, 3.4 и 4.1 ниже читать с этой поправкой.
- **Оболочка: Electron** (рекомендация планировщика). Клиент по-прежнему Three.js + React Three Fiber, собирается Vite в `apps/desktop`. Причины:
  - сохраняется общий TS-движок `arduino-core` для клиента и сервера, ради которого выбран R3F;
  - Electron несёт свой Chromium, поэтому WebGL одинаков на всех ПК. Tauri использует системный WebView (на Windows это WebView2, на macOS WKWebView, на Linux WebKitGTK), и поддержка WebGL там различается [предположение, проверить в P-01];
  - минус Electron — большой установщик (порядка сотни МБ) [предположение].
- **Альтернатива: Godot 4.** Это нативный движок с хорошим редактором. Но тогда симуляцию и проверку схем придётся переписать или держать только на сервере. Если владелец хочет Godot, это нужно решить до этапа 2.
- **Вход в приложении:**
  - экран входа с почтой и паролем того же аккаунта Supabase (публичный anon-ключ, как на сайте);
  - сессия хранится через `safeStorage` Electron;
  - «Регистрация» и «Забыли пароль» открывают сайт в системном браузере;
  - игровой сервер проверяет JWT, как в 4.1, пункты 4–6.
- **Скачивание:**
  - `/api/desktop/download` на сайте проверяет сессию и перенаправляет на подписанную ссылку установщика;
  - сведения о релизах лежат в манифесте или таблице `desktop_releases` (версия, платформа, контрольная сумма);
  - обновления через `electron-updater`;
  - где хранить установщики и нужна ли подпись кода — вопросы В18 и В19.
- **Тесты мультиплеера.** Два экземпляра приложения (Playwright умеет запускать Electron [предположение, проверить в P-01]) с двумя тестовыми аккаунтами. На этапах разработки допускается то же клиентское приложение в браузере через dev-сервер Vite. Это реальные клиенты, а не имитация.

### Р3: версию приложения определяет тариф

- **Рекомендуемая трактовка:** один установщик для всех. Набор доступного (лаборатории, размер комнат, функции) определяется **тарифом аккаунта** при входе и **проверяется на игровом сервере**. Отдельные сборки под тарифы не делаются: их можно передать другому человеку, при смене тарифа пришлось бы переустанавливать приложение, а проверку на клиенте легко обойти. Трактовку должен подтвердить владелец (В17).
- **БД:** новая таблица `public.entitlements`:
  - поля `user_id`, `plan` (`free|pro|school`), `valid_until`, `source`;
  - читать может только владелец записи, писать — только `service_role`;
  - отсутствие записи означает `free`.
- **Оплаты пока нет** [проверено: на `/app/pricing` написано «оплата пока недоступна»]. До подключения оплаты все аккаунты работают как `free`, Pro и «Для школ» показываются как «готовится». Состав тарифов в игре и платёжный провайдер — вопросы В17 и В20.
- **Страница тарифов.** Поскольку тариф определяет возможности приложения, `/app/pricing` в профиле **рекомендуется оставить** (вопрос В6). Нужно только переписать тексты с уроков в браузере на возможности приложения.

### Р4 (вопрос В13): сократить сайт, когда приложение будет готово

- **Критерий готовности:** установщик скачивается из профиля, вход работает, «Лаборатория 1» проходится двумя реальными аккаунтами на рабочем игровом сервере.
- **Новый порядок этапов:** 0 → 2 → 3 → 4 → 5 (развёртывание сервера и выпуск приложения) → **1 (сокращение сайта) последним**.
- До этапа 1 обучение на сайте продолжает работать без изменений.

**Технический риск ESP32 (важно).** Текущий движок `avr8js` эмулирует только AVR-микроконтроллеры (Uno). ESP32 — другая архитектура (Xtensa или RISC-V, в зависимости от модели), и существующий движок её не запустит. Свободного эмулятора ESP32 на JS, сопоставимого с `avr8js`, я не знаю [предположение]. Известные мне варианты:

- QEMU-сборка от Espressif — тяжёлый нативный процесс на сервере;
- облачный симулятор Wokwi — внешний платный сервис;
- собственная упрощённая модель поведения на уровне Arduino API без эмуляции процессора.

Компиляция под ESP32 тоже требует отдельного ядра `arduino-esp32` в compiler-service, и его объём намного больше ядра AVR [предположение]. Поэтому ESP32 выносится в **отдельный этап 6 после выпуска MVP**, а MVP поставляется с лабораторией на Uno. Перед этапом 6 нужно исследование P-02.

## 0. Новая концепция и обязательные ограничения

1. На сайте остаются только лендинг, вход, регистрация, восстановление пароля и личный профиль. Политика конфиденциальности `/privacy` тоже остаётся, так как она юридически нужна для регистрации.
2. Учебные страницы и навигация к ним убираются с сайта.
3. Обучение проходит в игре. Практика идёт в общем 3D-помещении с настоящим мультиплеером: авторитетный сервер и реальные подключения игроков.

Ограничения для всех этапов:

- Нельзя заменять мультиплеер ботами, фейковыми игроками, синхронизацией через `localStorage`/`BroadcastChannel` или записанными действиями. Для приёмки нужны два реальных клиента с двумя аккаунтами, подключённые к одному процессу игрового сервера.
- Учебные материалы не удаляются. Сначала их переносят в пакеты и помечают git-тегом, только потом страницы убираются с сайта (этап 0 перед этапом 1).
- Действуют правила `AGENTS.md`: русский текст в контент-файлах, цвета через токены, `pnpm build` и `pnpm lint` после каждой задачи, журнал в `docs/progress.md`, демонстрационные данные явно помечаются. Игру, ИИ и доступ нельзя показывать как доступные, пока это не подтверждено. На лендинге обучение в игре описывается как «в разработке».
- Next.js 16.4.1 отличается от привычных версий: перед изменением маршрутов, `proxy.ts` и `next.config.ts` читать `node_modules/next/dist/docs/`.

### 3.3 Выбор сетевого сервера

Рекомендация: **Colyseus** (Node, TypeScript): авторитетные комнаты, синхронизация состояния по схеме с дельта-патчами, переподключение, хук `onAuth` для проверки токена.

Отклонено:

- Supabase Realtime Broadcast/Presence. Клиенты пересылают сообщения друг другу, сервер не проверяет действия и не запускает симуляцию. Любой клиент мог бы выдать себе выполнение задания. Не подходит под «настоящий мультиплеер с серверной синхронизацией».
- Собственный сервер на `ws`. Возможен, но реконнект, дельта-синхронизацию и комнаты пришлось бы писать самим.
- Nakama. Отдельная инфраструктура (Go, Postgres), логика на TS через плагины. Для одной комнаты избыточно.

Версии `colyseus`, `@colyseus/schema`, `three`, `@react-three/fiber` фиксируются при установке на этапе 2 по текущему npm. Я их не проверял и номера не указываю.

### 3.4 Хостинг

- Клиент: маршрут `/play` в существующем Next-приложении на Vercel. Тот же домен, поэтому сессионные cookie Supabase доступны без дополнительного обмена.
- Игровой сервер: Vercel Functions не держат постоянные WebSocket-соединения, поэтому нужен отдельный хост с долгоживущим процессом: Render (уже используется для `compiler-service/render.yaml`), Fly.io или VPS. [предположение: ограничение Vercel на WebSocket проверить по актуальной документации на этапе 2]. Выбор и бюджет — В3.
- Один процесс сервера на старте. Горизонтальное масштабирование (Colyseus presence/driver на Redis) — после MVP.

### 3.5 Поток данных


## 4. Связь аккаунта сайта с игрой

### 4.1 Вход в игру

1. Пользователь входит на сайте. В профиле кнопка «Играть» ведёт на `/play`.
2. `src/proxy.ts`: matcher расширяется до `["/app/:path*", "/play/:path*", "/play"]`. Без сессии пользователь уходит на `/sign-in?next=/play` (параметр `next` добавить в `AuthCard` с белым списком путей, чтобы не было открытого редиректа).
3. Клиент получает текущий access token через `browserSupabase().auth.getSession()` и передаёт его в `join` без URL и без query-строки.
4. Сервер в `onAuth` проверяет подпись и срок JWT. Если в проекте включены асимметричные ключи подписи, проверка идёт по JWKS проекта, иначе через `auth.getUser(token)` с сервисным ключом. Какой режим включён в проекте `wjdxephhhedxertzgjnu`, **я не проверял**: Codex проверяет это в начале этапа 2 в панели Supabase или через MCP.
5. Сервер читает `profiles.display_name` и `role` сервисным ключом и кладёт их в состояние игрока. Email другим игрокам не передаётся никогда.
6. Токен истекает во время игры: клиент обновляет сессию через Supabase и отправляет `auth.refresh`, сервер перепроверяет токен. Если токен невалиден, сервер разрывает соединение с кодом 4001, клиент возвращает пользователя на вход.

### 4.2 Гости

Мультиплеер требует аккаунта: имя видно другим, результаты привязаны к пользователю. По умолчанию гостевой режим убирается (В4).

### 4.3 Будущий настольный клиент

Если появится нативная оболочка (В2): одноразовый код. Профиль создаёт запись `private.game_link_codes` (хэш кода, user_id, TTL 2 минуты, одно использование), приложение обменивает код на сессию через игровой сервер. В MVP не реализуется.

## 5. Первый играбельный сценарий: «Лаборатория 1 — Первый огонёк»

Основа — урок `lesson-1` из `src/content/course.ru.ts` и `src/domain/lessons/content/index.ts`: светодиод с резистором на пине 13, программа мигания, режим кода `fill`, проверка `pinBlinks` (пин 13, не меньше 3 переключений за 3200 мс).

### 5.1 Помещение

Одна комната-лаборатория примерно 12×12 м, стены и пол из примитивов. Внутри:

- **стеллаж деталей**: Arduino Uno, резистор 220 Ом, светодиод, 2 лишние детали (кнопка, потенциометр) для проверки выбора;
- **верстак** с посадочными местами и подсвечиваемыми контактами (координаты берутся из `referenceScene` урока и маппятся на плоскость верстака);
- **терминал кода** с текстом программы и тремя пропусками `___` (из `starter`);
- **рубильник «Запуск»**;
- **табло задания** с текстом `courseCopy[0].task` и понятиями `concepts`.

Модели в MVP: примитивы и простые glTF, созданные в проекте. Ассеты Wokwi двумерные, в 3D их не переносим. Бюджет на художественные модели — В10.

### 5.2 Ход игры (2 игрока, работает и в одиночку)

1. Игроки появляются в комнате, видят аватары и имена друг друга, двигаются (WASD/стрелки, мышь для обзора; на сенсорном экране — В11).
2. **Сборщик** берёт деталь со стеллажа (`E`): деталь «в руках» видна всем. Кладёт на посадочное место верстака. Соединяет контакты проводом: клик по пину A, затем по пину B.
3. **Программист** у терминала заполняет пропуски. В MVP каждый пропуск выбирается из 3–4 вариантов, поэтому все комбинации заранее компилируются в HEX-кэш (`pnpm hex:build`) и сервер не компилирует произвольный код. Пока один игрок редактирует терминал, у остальных он заблокирован, и все видят, кто редактирует.
4. Любой игрок дёргает рубильник. Сервер:
   - проверяет схему через `arduino-core/scene/check` относительно `referenceScene`;
   - если в схеме ошибка, выставляет состояние `run.error` с кодом и подсказкой (тексты `checker/errors.ru.ts`) и подсвечивает детали всем;
   - если схема верна, выбирает HEX по хэшу нормализованного кода и запускает `runner` в `worker_thread` на 3200 мс, затем прогоняет `BehaviorCheck`;
   - транслирует состояние пина 13 (по выборке трассы) — светодиод мигает у всех клиентов синхронно (временная метка сервера плюс интерполяция).
5. Если проверка пройдена, все участники комнаты, которые совершили хотя бы одно действие в этом прогоне, получают запись `game_results` и XP. Табло показывает «Лаборатория пройдена». Игроки без действий награду не получают, проверяется на сервере.

### 5.3 Вне рамок MVP

Произвольный код и живая компиляция, остальные 11 уроков, тесты из `lesson-quiz.ru.ts` в игре, ИИ-наставник, голосовой и текстовый чат, кастомизация аватаров, мобильная версия.

## 6. Серверная синхронизация

### 6.1 Комната `LabRoom`

- Максимум игроков: 4 в MVP (В12), комнаты по коду приглашения или автоматический подбор (В12).
- `setSimulationInterval` с тиком 50 мс (20 Гц). Клиент рисует со своей частотой и интерполирует чужих игроков с задержкой около 100 мс.
- Переподключение: `allowReconnection(client, 30)`. Пока игрок отключён, его деталь «в руках» остаётся у него. По истечении времени деталь возвращается на стеллаж, блокировка терминала снимается.

### 6.2 Состояние (`@colyseus/schema`, определяется в `packages/game-protocol`)

```
LabState
  players: Map<sessionId, Player{ userId, name, x, z, yaw, anim, holding?: partId, connected }>
  parts:   Map<partId, Part{ type, location: 'shelf'|'hand'|'bench', slot?, holderSessionId? }>
  wires:   Map<wireId, Wire{ from: PinRef, to: PinRef, authorSessionId }>
  code:    Code{ blanks: string[3], editorSessionId?, version }
  run:     Run{ status: 'idle'|'running'|'passed'|'failed', errorCode?, highlightIds[], pin13Timeline?, startedAt? }
  task:    { scenarioId, completed }
```

`userId` в состоянии нужен только серверу; клиентам он не рассылается (`@filter` или отдельное приватное хранилище в комнате).

### 6.3 Сообщения клиента → сервера (валидация на сервере)

| Сообщение                                                | Проверки                                                                                            |
| -------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `input {seq, dx, dz, yaw}` (до 20/с)                     | нормализация вектора, ограничение скорости, коллизии со стенами и мебелью на сервере                |
| `part.take {partId}`                                     | деталь на стеллаже, руки свободны, расстояние до стеллажа ≤ 2 м                                     |
| `part.place {slot}`                                      | деталь в руках этого игрока, слот свободен, дистанция до верстака                                   |
| `part.return`                                            | деталь в руках или на верстаке, проводов к ней нет                                                  |
| `wire.add {from, to}`                                    | оба пина существуют на установленных деталях, нет дубликата, лимит проводов                         |
| `wire.remove {wireId}`                                   | провод существует                                                                                   |
| `code.lock` / `code.set {index, option}` / `code.unlock` | лок свободен или принадлежит игроку; вариант из списка; `version` растёт                            |
| `run.start`                                              | `run.status !== 'running'`, дистанция до рубильника, ограничение частоты: 1 запуск в 3 с на комнату |
| `auth.refresh {token}`                                   | валидный JWT того же `userId`                                                                       |

Общие правила: лимит сообщений на сессию (например, 30/с, сверх лимита — отключение), схемы сообщений через `zod` (уже есть в проекте). Сервер не доверяет координатам и результатам клиента.

### 6.4 Конфликты совместных действий

Colyseus обрабатывает сообщения комнаты последовательно в одном потоке, поэтому порядок определяет сервер: первый `part.take` берёт деталь, второй получает `error {code: 'taken'}` и звуковой отказ. Терминал работает с эксклюзивной блокировкой: CRDT для MVP избыточен. Пока идёт запуск, изменения схемы и кода отклоняются.

### 6.5 Тяжёлые операции

Эмуляция avr8js идёт в пуле `worker_threads` (1–2 воркера), основной цикл комнаты не блокируется. Сервер замеряет время выполнения. Если очередь длиннее N, запуск получает отказ `busy`.

## 10. Риски

- **Р1. Пробел в обучении.** Если сайт сократить до готовности игры, у текущих пользователей не будет обучения (В13).
- **Р2. Нагрузка эмуляции на сервере.** avr8js в Node для каждого запуска. Для MVP хватит 3,2 с эмуляции на запуск и лимита частоты, при росте нужен отдельный пул или отдельный сервис.
- **Р3. Окружение.** `node_modules` на диске D через связи каталогов; workspace-пакеты и `transpilePackages` могут разрешаться иначе. На этапе 0 нужна проверка установки по процедуре из README.
- **Р4. Дети и общение.** Имена других игроков видны; чат не входит в MVP. Нужна модерация имён (В14).
- **Р5. Произвольный код.** В MVP только варианты из списка. Для свободного кода нужен изолированный `compiler-service` (Docker), нативный режим не изолирован и для игроков не используется.
- **Р6. Версии библиотек.** Номера версий Colyseus, three, R3F в плане намеренно не указаны; их совместимость с React 19.3 проверяется при установке.
