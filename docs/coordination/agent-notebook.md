# Блокнот координации агентов ArduHub

Общий рабочий журнал Claude и Codex по плану `docs/plans/arduhub-game-migration.md`. Раздел плана «Решения владельца от 11.11.2026 и поправки к плану» имеет приоритет над остальным текстом плана.

## Роли

- **Claude** (планирование и проверка): пишет задания, проверяет результат сам (команды, дифф, браузер) и выносит вердикт. Код не пишет.
- **Codex** — единственный исполнитель (по решению владельца от 11.11.2026; Astra — модель, на которой работает Codex, а не отдельный агент). Берёт задания, делает их, пишет отчёт. Упоминания Astra в плане относятся к Codex.
- **Владелец**: отвечает на вопросы `В1–В22` (раздел 11 плана и раздел поправок), читает раздел «Отчёт владельцу».

## Правила

1. Записи только **добавляются в конец** своего раздела. Чужие записи не редактируются и не удаляются. Исключение: Claude обновляет статусы на доске задач.
2. Каждая запись начинается со строки `### <дата> · <автор> → <адресат> · <ID задачи>`.
3. Исполнитель выполняет задачи **по порядку на доске**, берёт только задачи со статусом `ВЫДАНО` и не переходит к следующей зависимой задаче, пока Claude не поставил `ПРИНЯТО`. Независимые задачи со статусом `ВЫДАНО` можно делать подряд.
4. Отчёт исполнителя содержит: что сделано (файлы), какие команды запускались и их **фактический результат**, что не сделано или не проверено, вопросы. Без «всё работает» без вывода команд.
5. Если задание противоречит коду, `AGENTS.md` или здравому смыслу — исполнитель пишет вопрос вместо того, чтобы гадать.
6. Решения владельца записываются в раздел «Решения владельца» с датой; только после этого задачи, которые от них зависят, становятся `ВЫДАНО`.
7. Секреты, пароли, токены и email пользователей в блокнот не пишутся.
8. Общие правила проекта — `AGENTS.md`: `pnpm build` и `pnpm lint` после каждой задачи, запись в `docs/progress.md`.
9. Закончив работу, исполнитель ставит в своём отчёте статус `НА ПРОВЕРКЕ` и останавливается.

Статусы задач: `ЖДЁТ РЕШЕНИЯ` → `ВЫДАНО` → `В РАБОТЕ` → `НА ПРОВЕРКЕ` → `ПРИНЯТО` или `ДОРАБОТАТЬ`.

Для публичного кода оставить Docker isolation; native LOCAL_COMPILER не изолирован.

Артефакты ESP32 — application BIN и ELF, bootloader/partition BIN, при необходимости merged flash image с корректными offsets; это не AVR Intel HEX. Эмулятору нужен его поддерживаемый формат и ROM. Кэширование эталонов возможно как принцип, но требует нового контракта: `{board, fqbn, coreVersion, toolchain, libraries, options, partitionHash, sourceHash, format, artifactHashes}` и BIN/ELF/manifest вместо поля hex. Старый HEX-кэш напрямую неприменим; cache hit по одному коду между Uno/C3/classic недопустим.   - короткое замыкание замечается сразу при соединении проводов, по схеме из контекста;

- **Чат:**
  - открывается по клику на питомца или кнопкой урока «Спросить наставника» (событие `arduhub:mentor-open`, раньше в приложении не работала);

  - если сервер недоступен, честно показывается пометка «Ответ-заготовка».

**Подключение ИИ к приложению** (изменения на сайте):

- `src/app/api/mentor/route.ts` принимает `Authorization: Bearer <access token>` **только** вместе с `Origin: app://arduhub`. Для этого источника есть CORS (preflight) и не ставится cookie сайта. Токен проверяется Supabase (`auth.getUser(token)`), токены наставника списываются так же, как на сайте. Чужие источники и запросы без токена получают 403.
- `src/services/mentor/stream.ts`: `account(mentorId, request)` получает запрос (обратно совместимо).
- В приложении `/api/mentor` перенаправляется на `https://arduhub.vercel.app/api/mentor` с токеном сессии (`localApi.ts`). Адрес можно переопределить при сборке через `ARDUHUB_SITE_API`.
